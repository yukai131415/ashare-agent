## 一、基础与架构

### Q01：什么是 Agent Harness？【必问·通用】

**参考答案：** Harness 是模型之外的执行环境和控制机制。模型提出下一步行动，Harness 负责组装上下文、校验权限、执行工具、记录状态、验收产物，并决定继续、恢复或停止。它把不确定的模型行为纳入可观察、可约束的运行过程。

**追问：为什么不只是提示词？** 提示词是软约束，不能替代服务端鉴权、事务、超时和副作用控制。模型说“我没有越权”不构成权限证明。

**30 秒表达：** 我把 Harness 理解成 Agent 的运行底座：推理由模型完成，权限、执行、状态和验收由可信程序控制。

### Q02：Model、Agent、Harness、Workflow 有什么区别？【通用】

**参考答案：** Model 负责一次推理；Agent 围绕目标持续观察、决策和行动；Workflow 定义步骤、依赖和路由；Harness 支撑并约束执行。四者不是互斥产品，一个 Harness 可以运行固定 Workflow，也可以运行动态 Agent 循环。

**追问：是否一定有循环？** 一次调用也可以被 Harness 管理，但自主 Agent 通常涉及多轮决策。不能仅凭类名带 Agent 就证明其具备自主性。

### Q03：Harness 与 LangGraph、Agent SDK 的关系？【通用】

**参考答案：** LangGraph 等框架提供图、状态和运行能力，可以作为 Harness 的组成部分；应用仍需定义工具权限、业务验收、输入版本、数据隔离和副作用策略。不能说用了某框架就天然获得完整可靠性。

**项目表达：** 项目使用 LangGraph 编排业务角色，自建 Harness 补充跨任务统一的执行契约、运行账本和恢复边界。

### Q04：通用 Harness 如何分层？【必问·通用】

**参考答案：** 可以划分为入口与任务管理、上下文与规划、执行循环、工具/模型网关、状态与恢复、验证与交付；安全、预算和可观测性横向贯穿。分层是职责划分，不要求每层独立部署。

```text
请求/事件 → 任务目标与约束 → 上下文 → 模型决策/可信计划
                                       ↓
完成验收 ← 状态与反馈 ← 权限检查 → 工具执行
                ↑                         ↓
                └──── 检查点/失败恢复 ─────┘
横向：身份与租户、预算、审批、审计、取消
```

**追问：最小可用版本？** 一个任务循环、少量类型化工具、明确终止条件、权限检查、执行日志和产物验收即可，不必一开始上分布式队列。

### Q05：为什么不能靠更强的大模型解决可靠性？【通用】

**参考答案：** 模型能力可以减少推理错误，但网络超时、重复请求、越权、状态丢失和外部副作用是系统问题。强模型也无法从本地断线判断远端是否已写入，也不能替代数据库唯一约束。

### Q06：Harness 是不是必须有多个 Agent？【通用】

**参考答案：** 不是。单 Agent 也需要工具、状态、预算和安全边界。多 Agent 只是任务组织方式，会增加通信、成本和一致性负担，不能把 Agent 数量当作架构先进程度。

### Q07：什么时候使用固定流程，什么时候动态规划？【通用】

**参考答案：** 步骤明确、合规要求高时优先固定流程；开放式研究、信息不足时允许动态查询与规划。常见折中是固定阶段、阶段内动态行动，既保留探索能力，又限制越权和不可控执行。

**追问：动态计划如何落地？** 模型输出候选计划，经 schema、依赖、工具权限、预算与审批检查后才执行；模型不能直接生成 shell 并获得无限权限。

### Q08：控制平面与执行平面是什么？【通用】

**参考答案：** 控制平面管理计划、策略、权限、审批和任务状态；执行平面进行实际模型调用、数据查询和产物写入。划分后可以独立限制执行能力、追踪任务，并避免管理意见直接等同于执行成功。

### Q09：工具网关与普通 API 网关的差异？【通用】

**参考答案：** API 网关通常关注流量、身份和路由；Agent 工具网关还需要知道当前任务、阶段、允许动作、数据截止时间、剩余预算与副作用类别。两者可以叠加，不能互相完全替代。

### Q10：Harness 需要有哪些终止条件？【通用】

**参考答案：** 验收通过、业务合法弃选、不可恢复错误、预算耗尽、用户取消、等待审批和外部结果不明。成功、失败、弃选、待处理要分开，不能把“没有答案”统一算故障，也不能到次数上限就伪造成功。

### Q11：什么是完成条件与验收条件？【通用】

**参考答案：** 完成条件描述交付目标，例如生成可读取的报告；阶段验收检查每步结果，例如引用存在、金额对账、测试通过。模型自评可以辅助，但关键验收必须依赖可检查的证据或独立验证器。

### Q12：如何避免过度工程？【通用】

**参考答案：** 从真实风险出发。低风险只读问答不必引入复杂审批和 Saga；资金、发布、跨系统写入需要更强控制。先度量任务规模、执行时间、失败模式和成本，再决定是否需要队列、分布式锁或专门工作流引擎。

## 二、执行计划与工具

### Q13：一个可执行计划应该包含什么？【必问·通用】

**参考答案：** 至少包含计划版本、阶段 ID、依赖、输入输出契约、允许工具、验收规则和副作用分类。复杂系统还应有超时、重试、审批、补偿、租户和预算约束。

**项目区分：** 当前计划实际返回 version、task_type、steps、depends_on、allowed_tools、acceptance、effect 与 invariants；不是上面所有字段都已实现为计划字段。acceptance 主要是描述，真正检查还在执行器和业务代码中。

### Q14：计划工具与执行工具有什么区别？【通用/项目】

**参考答案：** 计划工具返回“做什么、按什么规则做”，执行工具产生查询、写入等实际效果。项目的 get_execution_plan 是只读计划检索，不会启动任务。模型读取计划后仍由应用与运行时执行，不能把“获得计划”说成“任务已经完成”。

### Q15：计划为什么需要版本号与内容指纹？【通用/项目】

**参考答案：** 版本号便于管理，内容指纹防止同名版本被改写而复用旧结果。恢复应绑定计划、输入和业务配置，防止在新流程里错误接续旧检查点。版本管理还应有不可变发布与迁移策略，指纹不能替代完整版本治理。

### Q16：为什么读取计划要 deepcopy？【项目】

**参考答案：** 计划模板存在进程内共享结构中，直接返回会让调用方修改嵌套列表，污染后续任务。深拷贝隔离返回对象。它保证内存层面的调用隔离，不代表模板存储已经实现签名校验或防管理员篡改。

### Q17：如何验证依赖图？【通用】

**参考答案：** 检查阶段 ID 唯一、依赖目标存在、无环、必要阶段可达，执行时再检查前置验收状态。动态计划还需要约束并行度与资源冲突。

**项目边界：** 当前模板是顺序依赖链，运行时逐步核对前置检查点，不是通用动态 DAG 编译器。

### Q18：Function Calling 的完整流程是什么？【通用】

**参考答案：** 应用向模型提供工具 schema；模型返回工具名、参数及关联标识；服务端校验后执行；将结果作为工具输出回传；模型据此继续调用或提交结论。模型产生工具请求，不会凭空执行本机函数。具体协议字段随接口变化。[来源 S1]

**追问：一次返回多个调用？** 按协议保存每个调用标识，根据依赖和写入冲突选择串行或并行；不能只执行第一个又把所有调用标成完成。

### Q19：有 JSON Schema 为什么还要业务校验？【通用】

**参考答案：** Schema 能约束结构、类型和枚举，但不能充分证明股票已实际查阅、财报在截止日前公开或选项未被风险否决。校验分为协议、结构、权限、领域语义和结果验收，不能只做 JSON 能否解析。

### Q20：MCP 与 Function Calling 的区别？【通用】

**参考答案：** Function Calling 是模型与应用协商结构化工具调用的机制；MCP 是应用连接工具/资源服务的一套协议。Harness 可以把 MCP 工具适配成模型可调用的工具。MCP Server 提供能力，不等于另一个模型，也不自动代表可信或已授权。

### Q21：工具如何设计才能减少模型误用？【通用】

**参考答案：** 单一职责、明确参数、有限枚举、安全默认值、明确时间范围与分页限制；返回来源、时间、状态和作用范围。避免万能 SQL、任意 URL 和任意代码执行接口，将读和写分离，错误明确是否可重试。

### Q22：模型生成无效 JSON 怎么办？【通用/项目】

**参考答案：** 先判断拒绝、截断、协议不匹配还是语法错误；给出简洁错误和一次有限纠正机会，并计入时间/调用预算。不能随意补括号、删除不认识的字段后发布，因为这会改变模型原意。项目的影子研究有结构化与语义校验及有界修正，不保证所有错误都能修好。

### Q23：工具描述里写“只读”就足够了吗？【通用】

**参考答案：** 不够。描述是面向模型的提示，权限必须由服务端身份和实际连接权限保证。例如只读数据库账号、SQL AST 校验、参数化查询和超时限制需要配合。只读工具仍可能泄露敏感信息或造成高成本查询。

### Q24：工具失败后应该返回什么？【通用】

**参考答案：** 返回结构化错误类型、作用范围、是否可重试、来源、追踪编号及可公开说明。区分“接口失败”“没有符合条件的数据”“没有权限”。不要把异常包装为空数组并标成功，也不要将单个股票失败扩写成全市场无资料。

## 三、状态、恢复与一致性

### Q25：检查点是什么，与缓存有什么区别？【必问·通用】

**参考答案：** 缓存主要降低查询成本，检查点保存一个任务阶段的已确认状态，服务于恢复和执行一致性。检查点通常绑定运行编号、计划/输入指纹、阶段状态、输出及尝试次数。即使查询缓存过期，历史已确认产物仍可能有审计价值。

### Q26：为什么不能只保存最终答案？【通用】

**参考答案：** 中途失败时无法知道哪些阶段成功、哪些工具已经调用或费用是否已发生。应保留阶段结果与关键证据，再在新进程中核对恢复条件。不是保存完整聊天文本就一定能恢复，还需要副作用状态与业务版本。

### Q27：什么情况下可以复用检查点？【通用/项目】

**参考答案：** 阶段已通过验收、运行身份与输入/计划匹配、产物完整且没有未确认副作用。时效敏感业务还需额外校验日期和数据有效期。项目正式恢复检查同日与配置一致；更改配置后应创建新任务，不能偷偷沿用旧中间结果。

### Q28：模型请求超时为什么不能直接重试？【必问·通用】

**参考答案：** 超时只表示本地没拿到完整结果，远端可能已经推理、计费或执行动作。需要区分发送前失败与发送后结果未知，利用请求编号、幂等能力或服务端查询确认；无法确认时暂停，不承诺“重试不收费”。

**例子：** 服务端生成完成后网络断线，本地重发会产生第二次请求。即使业务是只读查询，模型调用本身也有费用副作用。

### Q29：为什么先登记 sent，再发送请求？【项目】

**参考答案：** 为了避免请求已发出而账本没有记录的崩溃窗口。代价是登记后、真正发送前崩溃可能被保守判为未知，牺牲自动可用性换取避免盲目重复调用。sent 是发送意图记录，不是远端已接收的确证。

### Q30：收到响应但解析失败，用量算不算？【通用/项目】

**参考答案：** 算。业务结论失败不代表模型没生成或没计费。项目在收到响应时保留实际 usage 与回执，再做结构和业务验收。服务商没返回 usage 时标未知，不用字符数冒充真实 Token。

### Q31：为什么 exactly-once 很难保证？【必问·通用】

**参考答案：** 本地记录与外部写入通常不在同一个原子事务。外部成功、本地确认前崩溃会造成不确定窗口。实际常用至少一次投递配合幂等键、唯一约束和结果查询实现业务去重；没有外部幂等能力时保留人工核对分支。

**错误说法：** “加文件锁后就实现跨系统 exactly-once。”文件锁不能消除远程副作用与本地持久化之间的窗口。

### Q32：幂等、去重、互斥分别解决什么？【通用】

**参考答案：** 幂等强调同一业务请求重复执行不改变最终效果；去重识别已处理的业务请求；互斥防止同时执行。三者互补：锁释放后依然可能收到重复消息，去重记录丢失后又可能重复执行。

### Q33：幂等键怎么设计？【通用】

**参考答案：** 用稳定业务身份，如租户、业务日期、任务类型、对象及操作版本，不使用每次都变化的随机请求号替代业务键。参数指纹用于识别同键不同请求；保留处理状态、结果或结果引用，明确记录保留时间。

### Q34：为什么“先查询额度再扣减”不安全？【通用/项目】

**参考答案：** 并发请求可能都看到额度充足。项目用带条件的单条 UPDATE 原子增加恢复计数，并以受影响行数判断预占成功。预占后模型决定停止也可能占用一次恢复预算，因此它是安全额度预留，不等于每次都真实发生一次 Worker 重试。

### Q35：检查点与事件日志为什么要一起写？【通用/项目】

**参考答案：** 检查点面向当前状态读取，事件面向过程审计。同事务可避免状态变了却没有事件，或事件记成功而状态没更新。项目同一 SQLite 事务写检查点与阶段事件，但外部工具调用不因此自动进入同一事务。

### Q36：什么时候重试、补偿、人工处理？【通用】

**参考答案：** 可判定的暂时性错误考虑有限重试；已发生且可逆的业务效果考虑补偿；不可逆或结果未知的动作先核对。补偿是一个新的业务动作，不是数据库回滚，自己也可能失败，需要记录和权限。

### Q37：重试策略应该包含哪些内容？【必问·通用】

**参考答案：** 故障分类、最大次数、任务累计预算、总时限、退避/抖动、并发限制和幂等前提。对 429 应结合 Retry-After 与全局限流，不靠密集重试。401/403 多为鉴权或权限问题，重复调用通常无意义。

**项目边界：** 当前是有界配置退避，不应宣称已实现完整的指数抖动、全局令牌桶或服务商级熔断器。

### Q38：如何防止多层重试放大？【通用/项目】

**参考答案：** 明确唯一重试责任层，让底层网络尝试、Worker 恢复和调度重跑消耗共享或可关联预算。例如三层各三次可能放大到 27 次。项目通过运行内累计恢复预算及每日流水线尝试上限限制放大，但仍需监控不同调用路径是否全部纳管。

### Q39：文件锁可以替代分布式锁吗？【通用/项目】

**参考答案：** 不能。项目锁适用于单机进程互斥，Windows 使用字节锁，其他平台使用文件锁；锁由打开句柄持有，不是检查锁文件是否存在。多机要评估数据库认领、队列、租约和 fencing token，不能把本地锁文件放共享目录就声称可靠。

### Q40：什么时候需要人工审批？【通用】

**参考答案：** 高风险写入、权限提升、大额费用、不可逆动作或结果无法确认时。审批必须绑定具体输入和计划版本；审批后内容改变应重新审批。审批不是让用户对一段模糊摘要点击确认，也不能由执行 Agent 自己批准自己。

## 四、上下文、成本与多 Agent

### Q41：Context Engineering 与 Prompt Engineering 的区别？【通用】

**参考答案：** Prompt Engineering 侧重怎么表达指令；Context Engineering 还关注每轮放哪些证据、工具、历史、记忆与状态，以及如何检索、压缩和隔离。好上下文应与当前步骤相关、可溯源、足够新且不过载。

### Q42：为什么不把全市场数据一次塞给模型？【必问·项目】

**参考答案：** 会扩大费用、延迟和噪声，且可能挤掉关键证据。项目冻结可检索快照，先程序化多维探索，再由模型按需调用工具。可检索几千只不等于几千只都经过财务研究，页面必须区分检索范围和实际查阅覆盖。

### Q43：摘要压缩会带来什么问题？【通用】

**参考答案：** 容易丢失否定、时间范围、证据来源、数值单位和风险分歧。摘要应保留关键结构字段，原始证据仍可追查；不要反复摘要后把猜测变成事实。压缩策略也需要离线评测。

### Q44：为什么不能直接截断 JSON？【通用/项目】

**参考答案：** 截断可能破坏结构、丢掉尾部约束或证据，使解析失败或语义改变。应先减少工具结果字段、分页、按角色选择证据或分批处理。项目单次请求大小超限会拒绝，而不是截断请求体后继续发出。

### Q45：如何统计 Token 与成本？【通用】

**参考答案：** 优先保存服务商实际 usage，按调用去重并关联运行、阶段和模型。预估 Token 只用于预算，不能代替账单。成本还涉及计价版本、缓存输入、推理 Token 和工具费用，不能把总 Token 乘统一单价。

### Q46：如何降低多 Agent 成本？【通用】

**参考答案：** 先减少不必要角色、重复上下文和重复工具查询；共享可信证据、使用角色化摘要、缓存有时效定义的只读查询，并为简单任务使用规则或更经济的模型。用成本/成功任务、质量和 P95 延迟共同验证，而非只看调用次数减少。

### Q47：多 Agent 如何共享状态？【通用】

**参考答案：** 区分公共任务状态、角色私有上下文、证据库和最终产物，用明确 schema 合并。并行写入定义冲突策略与唯一键，不能让后返回的结果随意覆盖前者。共享原始聊天记录容易扩大泄露和提示注入范围。

### Q48：多个 Agent 使用同一个模型有意义吗？【通用/项目】

**参考答案：** 可能有意义，隔离的是职责、工具和上下文，而非一定使用不同模型。收益应来自更清晰的约束和验证，不应声称多个同模型角色投票就天然独立客观。相关性偏差仍然存在。

### Q49：没有调用 LLM 的 Worker 还是 Agent 吗？【通用】

**参考答案：** 工程命名没有统一标准，但需要准确描述自主程度。确定性采集器更适合叫 Worker 或工作流节点；整个系统可以混合规则 Worker 与模型 Agent。不要把“多个函数串联”当成完全自主多 Agent。

### Q50：长期记忆应该存什么？【通用】

**参考答案：** 经过确认且可复用的事实、偏好和经验，带来源、租户、时间、版本、有效期与撤销能力。执行检查点不是长期记忆，失败模型输出也不应未经验证写成权威知识。当前项目核心是账本与检索，不应包装为完整的自主记忆学习系统。

## 五、安全、可观测性与评估

### Q51：如何防止 Prompt Injection？【必问·通用】

**参考答案：** 外部网页、研报和工具输出是资料，不是可信指令；把可执行权限与文本内容隔离。实施工具最小权限、结构化提取、参数和业务校验、数据访问限制及高风险审批。提示词与检测器只是防线之一，不能承诺完全消除攻击。[来源 S2]

### Q52：多租户系统里应该隔离什么？【通用】

**参考答案：** 账号身份、密钥、检索空间、缓存键、任务、产物、日志和费用归属。服务端从会话确定租户，而不是信任客户端随意传 tenant_id。公共任务要明确共享数据与管理员权限，不能把公共展示变成任意租户可触发付费任务。

### Q53：如何防止工具 SSRF 与数据外泄？【通用】

**参考答案：** 优先业务化工具而不是任意 URL；限制协议、域名、地址解析、重定向和出口范围，阻断本机/内网敏感目标。凭据只在服务端注入，限制返回数据字段。仅做字符串前缀判断不够，出口网关和权限也重要。

### Q54：日志越详细越好吗？【通用】

**参考答案：** 不是。需要可定位但不过度泄露：记录任务/请求/阶段/工具编号、耗时、状态、错误类别、版本、回执和用量；凭据与敏感正文脱敏，必要原文进入受控存储。大量自动轮询日志会掩盖真正失败，应区分控制台、持久日志和采样策略。

### Q55：Trace 与普通日志有什么区别？【通用】

**参考答案：** Trace 将一次任务中的模型、工具、校验和角色调用串成因果结构；普通日志是离散事件。需要 run_id、span/parent 关系和可检查的状态。无需保存模型隐藏思维链，用行动、证据和结果即可调试。[来源 S3]

**项目边界：** 当前有运行、阶段和调用账本与日志关联，不应说已完整接入 OpenTelemetry 分布式 Trace 平台。

### Q56：为什么 MCP stdio 的 stdout 不能打业务日志？【项目】

**参考答案：** stdout 用于协议消息，混入普通日志会破坏客户端解析。项目把 MCP 模式的诊断输出路由到 stderr，同时保留本地日志；不能仅靠关闭所有日志掩盖问题。

### Q57：实时监控怎么判断任务真的结束？【通用/项目】

**参考答案：** 以持久状态和真实完成事件为依据；心跳超时只能表明失联，不能证明进程已终止。项目超过 10 分钟无新事件显示待确认，不会据此自动杀进程。完善方案还需要租约、外部进程管理与回收策略。

### Q58：Harness 怎么测试？【必问·通用】

**参考答案：** 分为确定性单元测试、协议集成测试、固定快照端到端回归、故障注入与真实模型小规模评测。重点覆盖工具越权、依赖失败、输入变更、重复执行、发送后断线、账本失败和无效证据。Mock 验证流程，不证明真实模型的语义质量。

### Q59：结构验收、语义评估和业务效果有什么区别？【通用/项目】

**参考答案：** 结构验收看步骤、依赖与调用状态；语义评估看结论正确、相关和有证据；业务效果看真实任务收益和用户价值。项目 audit 属于结构一致性检查，不等于股票收益评测，执行成功也不等于投资决策正确。

### Q60：如何评价一个 Harness 是否更好？【通用】

**参考答案：** 看任务验收成功率、危险动作拦截、未知结果率、重复副作用、恢复成功率、人工介入率、成本与延迟。固定模型和数据比较 Harness 变化，再固定 Harness 比较模型变化，避免混淆变量。用失败案例分层统计，不只看总体平均。[来源 S3]

### Q61：RAGAS、Recall@K、MRR 在这里是什么角色？【通用】

**参考答案：** 它们评估检索/生成环节，不覆盖整个执行可靠性。Recall@K 关注相关资料覆盖，MRR 关注首个相关结果位置；RAGAS 可评估上下文召回、精确度、回答忠实与相关性。还应有权限、安全、幂等和业务验收，不能拿高检索分数证明完整 Agent 安全。

**项目边界：** 当前投研仓库有 Milvus 检索，不应据此宣称已具备企业简历项目所写的整套 RAGAS、BM25 或 reranker 基准结果。不同项目的指标不能混用。

### Q62：如何做版本发布与回归？【通用】

**参考答案：** 版本化计划、提示词、工具 schema、模型配置和验证器；保存脱敏样本进行回归，按风险设置上线门槛。影子运行只观察不影响正式输出，之后灰度与监控；旧任务恢复必须有版本兼容策略，不能任意套用新代码。

## 六、当前项目专项问答

### Q63：请用两分钟介绍项目。【必问·项目】

**参考答案：** 我独立建设了一套 A 股投研辅助系统，最初围绕行情采集、特征分析、回测和规则推荐形成流水线，之后引入 LangGraph，将数据、基本面、技术面、风险与决策职责拆开。正式推荐仍由原规则引擎决定，模型解释不改评分；影子研究独立运行模型工具循环，可以作出不同选择或弃选。

随着模型和工具调用增多，我发现难点不只是提示词，而是失败后能否安全恢复、重复调用是否会计费、阶段状态是否可信。因此增加 Harness：通过只读计划工具统一步骤和权限，运行时校验依赖并保存检查点，网关记录工具与模型回执，策略层限制恢复。管理员可以查看运行状态与修复记录。

目前它是单机、受限恢复的研究系统，不自动交易，不任意改代码，也没有证明稳定超额收益。我的重点是把模型能力放入可追踪、可验证的工程边界。

### Q64：为什么要改造 Harness，原来不行吗？【项目】

**参考答案：** 原来已有业务校验、日志、重试和持久化，但分散在模块中，任务级状态和恢复条件不够统一。改造是把计划、阶段执行、调用档案和累计预算集中管理，而不是说原系统完全无状态或无权限校验。收益主要是边界一致和可追踪，尚不能虚构量化故障率提升。

### Q65：当前真实目录怎么分层？【项目】

**参考答案：** planning 定义计划；runtime 执行与复用检查点；gateway 管调用边界；context 管请求指纹与大小；persistence 管 SQLite；policy 管错误分类与预算；locking 管单机互斥；control/master 管主模型协调；adapters/llm 管服务商协议；evaluation 管离线轨迹检查。原 agents、selection 等保留业务计算，Harness 不计算股票分数。

### Q66：正式与影子谁真正使用大模型？【项目】

**参考答案：** 正式链主要由确定性 Worker 和规则引擎执行，角色解释可配置启用模型，但不改股票评分或顺序；主 Agent 可调用模型给出受限协调意见。影子基本面、技术、风险和决策角色使用模型，通过原生工具调用查询和提交结构化意见。盘中分析也有模型调用。不能说每个采集 Worker 都有自主推理。

### Q67：主 Agent 是不是自主调度器？【必问·项目】

**参考答案：** 当前不是自由调度器。分发阶段允许动作只有 dispatch，模型确认可信计划，真实执行仍由既定图负责。故障恢复先由程序判断是否有资格，再让模型在 retry/stop 等允许动作中选择。它没有 shell、代码编辑或策略变更权限。

**追问：既然只有 dispatch，调用模型价值大吗？** 目前执行正确性不依赖这次模型调用，它更偏受限协调实验；如果成本收益不明显，可以规则化分发，把模型留给复杂诊断，不能为“主 Agent”名义增加无必要调用。

### Q68：模型不可用会发生什么？【项目】

**参考答案：** 主控协调可以使用明确标记的规则兜底，保留固定图与安全校验；这不意味着影子决策能伪装成规则推荐。影子模型链失败应显示失败/待处理，不把正式推荐复制成影子模型结论。不同调用路径的降级语义必须分别描述。

### Q69：目前有哪三套计划？【项目】

**参考答案：** 正式是采集冻结→财务审阅→原策略排名与回测→风险检查→保存推荐；影子是多维准备→基本面→技术→风险→独立决策；盘中是行情→辅助分析→时段持久化。三个计划都来自 get_execution_plan，但验收细节分别在原业务代码与运行时完成。

### Q70：数据库有几类，为什么不全部合并？【项目】

**参考答案：** Harness 新增 runs.db 保存运行、检查点、事件、工具和模型调用；原推荐、影子、盘中、账号及 agent_control 业务记录保留。这样降低迁移风险并维持职责分离。代价是跨库状态一致性不由单一事务保证，需要审计和核对，不应宣称已经解决跨库原子提交。

### Q71：实际恢复入口是什么，哪些不能恢复？【必问·项目】

**参考答案：** CLI 的 resume 目前开放正式任务，要求相同运行、配置、计划及同日非回放输入；成功阶段复用检查点。影子同一个实验实例重新进入可以恢复配套状态，但没有新增旧报告自动恢复入口；盘中已认领时段不自动重放。发布或模型调用结果不确定会拒绝自动重跑。

**追问：可以直接改数据库状态吗？** 不建议。会破坏副作用与计费判断，必须先核对外部结果；当前没有完整人工批准重放接口，必要时创建有明确授权的新任务。

### Q72：为什么影子检查点要保存 evidence 和 observed？【项目】

**参考答案：** 只有模型文字无法恢复证据引用、查阅覆盖和用量。项目 capture 保存结论、证据、已查阅代码、调用数、输入字符、usage 与报告字段，restore 重新建立实例状态，防止复用结论后证据 ID 不存在或忘记前面已消耗的预算。

### Q73：全市场按需查询实际怎么做？【项目】

**参考答案：** 先冻结已采集且通过准入的公开行情快照，不是保证所有上市公司都有数据。准备阶段分别按成交额、涨跌幅、换手率、正市盈率检索，每维前 5 只，去重最多 20 只，再集中查财务和风险。模型可以继续按条件/分页查询，不受旧的固定 12 只池限制。

**追问：查了 20 只就证明覆盖全市场了吗？** 不能。只是检索扫描范围可能覆盖整个冻结快照，深度研究仍只覆盖被展开并核验的候选。多维探索也有选择偏差，不代表全市场最优。

### Q74：目前到底有哪些预算？【项目】

**参考答案：** 新全市场模式每轮最多展开 60 只行情，search_market 每页 1–20 只；影子总模型请求上限 16 次、总时间 300 秒，单次输入序列化字符上限 100000。累计 30000 Token 和累计输入字符停止阈值已取消，服务商限制仍存在。旧模式保留不同上限，必须区分新旧路径。

**追问：取消 Token 上限是不是无限运行？** 不是，时间、调用数、工具范围和单请求大小仍约束执行。恢复和格式纠正也不能绕过总预算。

### Q75：默认恢复政策是什么？【项目】

**参考答案：** RecoveryPolicy 默认最多两次 Worker 重试、运行累计恢复预留最多六次、退避一秒，HTTP 候选白名单为 408/429/500/502/503/504，允许收窄；具体配置可覆盖但受范围校验。每日流水线尝试默认最多三次。HTTP 可重试也要满足幂等、预算和调用确定性，不代表任何路径都自动重试。

**补充：** 财务传输遇到鉴权/限流有自己的快速失败语义，不能用主策略存在 429 就说所有财务 429 都会重试。是否恢复必须结合实际路径。

### Q76：如何把运行上下文传给线程池？【项目】

**参考答案：** 使用 ContextVar 保存当前 Harness 与阶段，日志也关联运行信息。行情与新闻并行采集时，每个提交任务独立 copy_context().run，避免线程丢失上下文；同一个 Context 不可同时进入多个线程。它不是持久化机制，进程重启后要靠账本恢复。

### Q77：盘中 10 分钟任务怎么避免重复和时间错配？【项目】

**参考答案：** 根据上一交易日目标形成观察列表，在交易时段按日期/时段/股票唯一键先认领记录，再抓行情和调用模型。请求跨时段则拒绝把新行情记作旧快照；已认领时段不自动重放。累计成交额差值只在不回退时计算区间额，分析区分观察与推测，不把“主力意图”当作可直接证实的事实。

### Q78：监控中的“修复次数/成功次数”如何计算？【项目】

**参考答案：** 每次启动受限重试记一次修复尝试；同一运行同一 Worker 后续真实成功才记恢复成功，多次重试最终成功只计一次。它不等于主模型调用次数，也不等于任务累计恢复预算预留次数。监控事件库与 Harness 阶段账本是不同视角。

### Q79：为什么选 SQLite，而不是直接上 PostgreSQL？【项目/设计】

**参考答案：** 当前单机研究场景优先简化部署和事务操作，SQLite 适合中低写并发；连接及时关闭，用唯一约束与原子更新控制关键状态。高写并发、多实例和远程管理增长后再评估 PostgreSQL 与队列。不能声称 SQLite 能线性扩展到任意高并发。

### Q80：项目当前有哪些明显不足？【必问·项目】

**参考答案：** 单机进程内为主，没有分布式队列、远端取消和进程级守护；没有服务商账单自动对账及人工批准重放闭环；历史计划不可变归档与审计还需加强；部分旧路径未完全纳入统一调用账本，工具权限拒绝发生在归档 try/finally 之前也可能缺少专门拒绝记录。现有日志脱敏不等于已完成全部敏感信息合规审计。

**追问：还有业务评估短板吗？** 有。轨迹结构通过不证明模型研究正确，事后最高价模拟不等于可成交收益，多维前几名样本不是全市场代表性实验。

### Q81：现在测试全部通过吗？【真实性·项目】

**参考答案：** 不能讲“全部通过”。最近一次记录为 220 项中 219 项通过，同日推荐锁定集成用例缺少 locked_daily_recommendation 字段报错，单独复测仍失败。曾跨午夜运行只是排查线索，不是已证实根因。该问题尚未在本次题库任务中修复或重新验证。

**面试表达：** 我会先固定时钟和数据重现，再检查日锁分支、数据日期与 metadata 契约；补充回归后才能更新测试结论。坦诚具体问题，比把失败隐藏成“环境问题”更可信。

### Q82：下一阶段你会优先做什么？【项目规划】

**参考答案：** 第一修复并稳定现有回归，固定时钟避免时间敏感测试漂移；第二补计划不可变归档、调用拒绝审计和统一调用身份；第三完善人工核对/审批闭环与费用对账；第四建立固定快照语义评测和安全攻击集。只有任务规模证明需要时，才引入分布式队列与租约。

## 七、场景追问与 Java 迁移

### Q83：工具写入成功，进程在写检查点前崩溃，怎么办？【场景】

**参考答案：** 不直接重跑。先用业务幂等键或外部请求编号查询结果，能确认则补本地产物与状态；无法确认则待核对。将来可以增加 outbox、外部幂等接口与 reconciliation worker，但不能说当前项目已经有完整实现。

### Q84：模型连续查询同一个工具，怎么防循环？【场景】

**参考答案：** 对工具名与规范化参数做指纹，检测无新增信息的重复；缓存可复用查询并提示已查结果，设置总轮数、时间和费用预算。业务上无进展时要求收敛或停止。不能仅靠温度调低，也不能把不同 as_of 的查询错误合并。

### Q85：前置阶段失败但最终状态显示成功，怎么排查？【场景】

**参考答案：** 对照 run_id 的阶段事件、检查点和报告，确认失败是否被异常吞掉、后续是否跳过却计成功、前端是否显示历史结果。最终成功应要求所有必需阶段验收。项目 finish 有完整阶段检查，但 audit 只看当前状态与依赖，尚不能证明完整历史时序正确。

### Q86：多实例部署时怎么升级？【场景·未来】

**参考答案：** 使用持久任务队列或数据库认领，租约、心跳和 fencing token 防旧 Worker 继续提交；状态放共享数据库，产物放受控对象存储。重新投递需要幂等，取消要区分未开始、执行中与外部已发送。不能只把文件锁换 Redis 锁就认为改造完成。

### Q87：怎么把 Java 后端经验迁移到 Harness？【必问·个人优势】

**参考答案：** 任务恢复对应状态机和事务边界，防重对应唯一键和幂等，工具权限对应服务端鉴权，重试预算对应限流和熔断，调用审计对应链路追踪。区别是 Agent 动作由模型动态提出，需要额外处理不可信文本、结构化参数与证据验收。我复用后端工程原则，不把模型当可靠事务协调器。

### Q88：用 Java 实现会怎么选型？【通用·设计】

**参考答案：** 可以用 Spring Boot 提供任务与管理 API，类型化 DTO/Bean Validation 校验工具参数，数据库保存任务与检查点，线程池或队列执行阶段，用统一拦截器记录调用。是否使用特定 Agent 框架看协议、持久化和治理能力，不因为换语言改变幂等、审批与未知结果处理原则。这里是设计方案，不是本项目已经用 Java 重写。

### Q89：Human-in-the-Loop 如何防止审批后内容被改？【场景】

**参考答案：** 审批记录绑定租户、计划版本、参数指纹、产物版本、审批者与有效期，执行前再次比对。修改 SQL、金额、收件人或数据范围后必须重新审批。审批事件审计与执行权限分离，不能让前端一个 approved=true 就越过后端。

### Q90：如何回答“你做的只是几个 API 拼起来”？【综合】

**参考答案：** 工具接入本身确实不是核心壁垒。我的工程工作在于约束动态调用：定义任务与阶段契约、处理不同服务商协议、保留证据和真实用量、解决失败与重复副作用、隔离影子和正式结果，并用测试验证边界。我也会明确目前只是单机底座，不包装成通用企业级自主平台。

## 八、可以直接练习的项目表达

### 30 秒版

我做的是一套单机多 Agent 投研辅助系统。正式推荐走可复现规则，模型研究走独立影子链。我把计划、阶段执行、工具权限、检查点和调用审计统一到 Harness，重点解决失败后从哪里恢复、哪些调用不能重放以及如何确认真实成功。系统不自动交易，也不让模型任意改代码。

### 3 分钟版提纲

1. **业务背景：** 多来源行情、财务和研报需要按时间边界组织，正式规则与模型研究必须分离。
2. **原始痛点：** 状态分散、模型 JSON 失败、上下文膨胀、重试重复消耗、前端难定位阶段错误。
3. **方案：** 可信模板计划 + LangGraph 编排 + Harness 执行器 + 工具/模型网关 + SQLite 账本。
4. **技术难点：** 模型已发送但回执丢失，不能将超时简单等同失败；成功检查点必须绑定输入与计划。
5. **实际落地：** 真实阶段状态、工具白名单、多维按需查询、证据校验、有限恢复、管理员审计。
6. **验收方式：** 离线流程与故障测试、协议检查、固定快照回归；保留尚未通过的用例与真实验证边界。
7. **不足与规划：** 没有分布式接管、自动账单对账或完整人工重放审批；优先完善这些闭环而非无限加 Agent。

### STAR 案例：模型超时后的安全恢复

- **S：** 多阶段任务会遇到模型网络异常，粗暴重试可能重复计费，且页面只知道阶段失败。
- **T：** 让执行层区分未发送、已收到和结果不明，并阻止未知调用自动重放。
- **A：** 在网关发送前登记状态，响应到达时归档 usage 和请求回执；阶段恢复检查未确认调用，配合输入指纹、进程锁与检查点。
- **R：** 已形成可审计的保守恢复分支，离线用例覆盖发送后超时阻断和解析失败仍保留 usage。没有据此宣称费用降低某个百分比或消除所有重复计费。
